# Talk Narrative — Goatmire 2026

Title: **Zero Alert Storms: Formal Verification for IoT Automation** Format: 30 minutes plus Q&A Implementation: this public, simulation-only repository

The talk is a narrow demonstration of a deployment-gate pattern. It is not a production case study, a physical-IoT showcase, or a claim that one formal model proves a whole automation platform safe.

The currently exposed conference introduction is recorded and corrected in [`public-abstract.md`](./public-abstract.md). The replacement should be sent to the organiser and treated as the only approved public copy.

## One-sentence argument

When independently reasonable automation rules interact, a deterministic formal gate can reject encoded conflicts before deployment, while an LLM can help a human understand the running system without becoming the judge.

## What the audience actually sees

- a supervised, simulated fleet and a synthetic shift-change load;
- a rule pair reproduced from SOTERIA's published O3/O4 conflict shape;
- Maude returning `clean`, `conflicts`, or `unverified`;
- observe mode recording a conflict without blocking deployment;
- enforce mode withholding the conflicting rules under the same staged load;
- BeamLens answering a natural-language diagnostic question from a bounded, read-only telemetry snapshot;
- a visible provider boundary: Codex using included ChatGPT-plan usage when available, with a fixed local Ollama model as fallback;
- Grafana or Prometheus only as raw-metric corroboration.

No physical device is used on stage. MQTT, VDA 5050, Modbus, HTTP ingress, and declared-device modules remain off-stage adapter examples. They do not support a hardware claim and are not evidence for the demo result.

## The research-derived opening

Do not invent or imply a personal outage. Start with a demonstrated failure shape from the literature:

> In SOTERIA's multi-app evaluation, two apps identified as O3 and O4 respond to the same contact-sensor-open event by setting a switch to conflicting values. Each automation can look reasonable by itself; the unsafe or surprising behavior appears in their composition.

The repository encodes a controlled reproduction of that pair with its own rule IDs. It does not copy the applications, reproduce a harmed household, or show that Maude historically prevented the published violation.

This is a stronger and more honest “IoT horror story” angle: peer-reviewed work establishes that cross-app interactions are a real problem, while the demo limits itself to reproducing an exact conflict pattern it can inspect.

Use the other sources to establish breadth, not to pile on anecdotes:

- **SOTERIA** models multi-app safety properties and reports conflicting switch actions for shared events.
- **HOMEGUARD** shows that individually secured apps can still create cross-app interference and checks collective rule semantics at installation.
- **AutoIoT** pairs LLM-generated automation with a separate automated conflict check, supporting the talk's separation between probabilistic generation or explanation and deterministic checking.
- **IoTCheck** independently studies smart-home application conflicts with model checking. It is useful corroboration that this is not a taxonomy invented for the demo.

Primary links and the exact claims they support are in [`reading-list.md`](./reading-list.md).

## Trust boundary

The formal and diagnostic paths have different jobs:

| Component | May do | Must not be presented as |
|---|---|---|
| Maude / ExMaude | decide the encoded conflict predicates | proof of omitted hazards or production safety |
| Engine | observe or enforce the returned verdict | a production control plane |
| Telemetry sampler | expose a bounded structured snapshot | complete historical evidence |
| BeamLens | select read-only diagnostic callbacks and structure an answer | an actuator or deployment interface |
| Codex / Ollama | explain observations and suggest what a human should inspect | the formal decision maker |
| Grafana / Prometheus | show raw source fields | the primary diagnostic experience |

The stage line is:

> Maude decides the encoded conflict. The model explains a bounded snapshot of what the running BEAM system observed. If they disagree, trust the structured fields and the Maude verdict—not the prose.

BeamLens exposes exactly three custom, read-only callbacks: snapshot, current verification, and recent alerts. It has no deploy, command, or physical-action callback. The stage path sends one schema-constrained provider completion over the BeamLens skill's bounded snapshot and has one thirty-second deadline. Exact evidence lines are rendered from the snapshot rather than generated by the model. The iterative BeamLens coordinator remains in the full inspector with a six-turn cap; telemetry history is bounded to five minutes.

## The two design claims

### One rule representation, two consumers

`Goatmire.Rules` produces the term, `Goatmire.Verifier` submits it to ExMaude, and `Goatmire.Engine.RuleEval` executes it. The gate therefore checks the artifact that runs rather than a parallel document that can drift.

### Three verdicts

The result is `clean`, `conflicts`, or `unverified`. A backend timeout, crash, or malformed response is not evidence of conflict freedom. Observe mode may deploy known conflicts for the controlled comparison, but neither mode deploys an `unverified` set.

The UI must keep the scope sentence adjacent to every result:

> No encoded conflict was found in this rule set. This does not prove physical safety, temporal correctness, authorization, or any omitted property.

## Thirty-minute arc

### Act 1 — Composition is the problem (about 5 minutes)

Open with the SOTERIA-derived contact-open pair. Show why reviewing each rule alone misses an interaction. Introduce the synthetic alert storm as the behavioral consequence the simulator will make visible, not as a real outage.

### Act 2 — A narrow formal gate (about 9 minutes)

Explain Maude through familiar Elixir ideas: sorts as domain types, operators as constructors, and equations or rewrite rules as executable semantics. Show the shared rule representation, trinary verdict, witness, and the three conservative partition edges: same Thing, same action target, and writer-to-trigger property. Avoid universal latency or scale claims.

### Act 3 — Observe, enforce, then ask the system (about 10 minutes)

Run the same staged shift change — same fleet size, tick rate, and shift parameters — once in observe mode and once in enforce mode. Read counters from the screen. Then ask BeamLens why alerts rose, which formal verdict accompanies the run, and what to inspect next. Point to its cited fields, observation/inference split, grounding, and active provider. Use one raw Grafana field only if corroboration helps.

### Act 4 — Generalize without widening the proof (about 4 minutes)

Connect the pattern to LLM-generated rules: generation and explanation may be probabilistic; permission to deploy remains deterministic. State what the model omits, point to the benchmark task in the repository, and invite the audience to try the code.

### Buffer and transition (about 2 minutes)

Reserve this for provider fallback, browser movement, and the final scope sentence. The formal demo remains complete if both diagnostic models are unavailable.

## Performance language

Never repeat the old `~500 µs` claim or a universal scale number. The benchmark artifact must carry:

- git commit and dirty state;
- runtime and interpreter context;
- rule count and partition count;
- pairs considered and skipped;
- verdict;
- median and p95 across warmed runs.

Acceptable stage language:

> On this laptop, with this commit and encoded rule set, the warmed runs shown in the artifact produced this median and p95. Different models, partitioning, interpreters, and hosts need their own measurement.

## Demo failure hierarchy

1. If Codex is unavailable, show the visible reason and let Ollama answer.
2. If both models are unavailable, read the structured snapshot and optionally open Grafana. The formal claim is unaffected.
3. If Maude is unavailable, demonstrate `unverified` and fail-closed behavior. Do not substitute an LLM opinion.
4. If the support containers fail, use local transport and the host simulator.

## Speaker discipline

- Say “simulation” before showing any counter.
- Say “research-derived reproduction” before showing Scenario 1.
- Say “observe” and “enforce,” not “gate off” and “gate on.”
- Read live numbers; never memorize rehearsal counters.
- Name the diagnostic provider and privacy boundary.
- Attribute deterministic decisions to Maude, never to Codex or Ollama.
- Use “conflict detected” for a witness and “no encoded conflict found” for a clean result.
- End with what remains unproved.
